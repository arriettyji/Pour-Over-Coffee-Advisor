# 个人上下文与渐进建档

## 一、运行目标

个人资料用于减少重复输入、确认实际可用器材并校准方案。固定理论、运行时对象研究和案例分析承担专业能力，因此缺少个人档案时仍能完成首杯设计、诊断、迁移与比较。

根据可用资料选择以下状态：

| 状态 | 可用内容 | 运行方式 |
|---|---|---|
| 无档案 | 当前请求和附件 | 直接研究与分析；只在关键缺口会改变整体方向时集中询问一个问题 |
| 会话级档案 | 当前对话中逐步确认的信息 | 每轮合并新事实，后续轮次直接继承，并接受最新纠正 |
| 持久私人档案 | 用户选择保存的独立文件或 Personal Context | 跨对话加载相关字段，再由当前请求覆盖 |

## 二、无档案模式

收到第一次请求时，先判断当前信息是否足以形成合理方案。信息足够时直接完成任务；关键字段缺失时提出一个高价值问题，同时给出带条件说明的初步判断。

完整建档属于可选后续步骤。用户没有表达长期使用或保存意图时，把新信息留在当前对话中，不以建档流程延迟本次冲煮建议。

## 三、会话级私人档案

在同一对话内维护一份结构化的运行状态。每轮从用户新消息中提取与后续决定有关的明确事实，并按以下类型合并：

1. 咖啡与当前样品状态；
2. 已拥有、当前可用、临时借用、耗尽或停用的器材与耗材；
3. 器材规范身份、用户简称与检索别名；
4. 计时起点、单位、默认粉量、默认闷蒸和其他稳定操作；
5. 当前目标、稳定偏好、探索与风险倾向、有限豆量策略和明确排斥方向；
6. 单次冲煮参数、过程与感官结果；
7. 用户对旧信息的纠正、替换和版本变化。

每条状态使用以下最小结构：

```yaml
- kind: identity | inventory | default | preference | constraint | observation | correction | hypothesis
  value:
  scope: profile_global | session_global | coffee_case | brew_attempt | response_only
  applies_to:
  expires_after:
  source_turn:
  status: confirmed | provisional | historical | corrected
```

冲煮观察另行保留证据粒度，避免把整杯结果拆成未经证明的参数规律：

```yaml
- observation_id:
  case_id:
  brew_id:
  configuration:
  process_observation:
  sensory_observation:
  user_interpretation:
  causal_status: whole_configuration_observation | contrasted_effect | repeated_pattern
  direct_scope: exact_brew
  transfer_status: case_evidence | candidate_prior | confirmed_profile_rule
  independent_record_ids: []
```

器材对象另用规范实体记录，避免同一实物因简称、旧名或旧材质描述重复进入库存：

```yaml
- canonical_id:
  canonical_name:
  inventory_label:
  aliases: []
  manufacturer:
  model:
  version:
  size:
  material:
  objective_structure:
  compatible_filter_interfaces:
    - interface_id:
      shape:
      nominal_size_model:
      forming_method:
      required_tool_component:
      applicable_bases: []
      compatibility_source:
  source_urls: []
  verified_at:
  distinguishing_features: []
  availability_role: owned_current | session_available | borrowed_this_brew | historical_use | purchase_record | unknown
  availability_source:
  status: confirmed | provisional
  search_seed: []
  confirmed_at:
  identity_notes:
```

`scope` 按以下范围使用：

| 作用域 | 内容 | 默认继承 |
|---|---|---|
| `profile_global` | 长期器材身份、计时规则、个人默认值和已确认稳定偏好 | 可进入不同咖啡，由当前请求临时覆盖 |
| `session_global` | 用户明确指定当前对话所有案例共同采用的临时规则 | 在当前对话持续到用户修改或会话结束 |
| `coffee_case` | 当前咖啡的样品状态、剩余量、目标、历史结果和对象级限制 | 只进入同一咖啡的后续冲煮 |
| `brew_attempt` | 下一杯指定的滤杯、滤纸、水、操作或实验要求 | 完成该方案或用户改变要求后到期 |
| `response_only` | 补充解释、引用、格式和比较角度 | 完成本次回答后到期，不改变配方 |

把新信息放入能够准确解释用户原话的最小作用域。只有用户明确说“以后都这样”“所有咖啡都这样”“这是我的默认”时，才提升到 `session_global` 或 `profile_global`。一次冲煮采用的器材、温度、闷蒸或注水结构属于对象观察或单次方案，不自动升级为广域约束。

为每项标记确认状态：

- `confirmed`：用户明确陈述或持久档案已有确认；
- `provisional`：来自模糊照片、简称、助理匹配或待确认信息；
- `historical`：曾经拥有、使用或适用，目前只用于解释历史；
- `corrected`：已经被更新信息替代，只保留来源关系。

合并时遵循以下规则：

1. 当前消息中的最新明确纠正优先于同一对话早期内容和持久档案。
2. “我有”“我现在还能用”支持库存状态；“这杯用了”只支持本次使用，无法单独区分自有、借用或已耗尽库存。
3. “我一般”“我的默认”支持个人默认；一次配方中的数值保留为案例参数。
4. 一次感官结果保留在当前对象案例，直接作用范围为对应 `case_id + brew_id`；同一记录被再次提及仍算 1 条证据。跨对象重复模式先确认来自独立冲煮、提取共同边界并进入候选，经过用户确认后再升级为稳定偏好。
5. 只有与本轮决定相关的信息进入分析和输出，避免展开无关私人资料。
6. 新咖啡建立新的 `coffee_case`，继承 `profile_global` 和仍然有效的 `session_global`，保留其他咖啡案例供回看，但不复制其对象级与单次条件。
7. 用户纠正某个字段时，只替换 `applies_to` 指向的目标字段；库存纠正不重写感官历史，参数纠正不自动改变个人默认。
8. 跨对话持久资料只读取唯一文件 `private-coffee-profile.md`。不得创建、合并或维护平行的对象登记、环境摘要或旧版主档；当前消息和会话已确认状态优先于该文件。
9. 商品图片、产品页、文章或比赛资料只证明外部对象或其声明；购买凭证先记为 `purchase_record`，用户明确持有、当前权威库存或本轮明确可用才进入当前库存。图片标题、文件名或助理先前的对象映射不能替代用户确认。

### 器材实体归并与可用性台账

任何器材筛选都先完成身份归并，再判断是否可用。具体流程如下：

1. 收集当前请求、会话状态、唯一私人主档、冲煮记录和购买记录里的当前有效称呼，并保留各自来源角色；
2. 使用用户已确认的规范身份、尺寸、材质、代际、联名、底部组件和其他区分特征，把当前简称解析到唯一 `canonical_id`；
3. 私人主档只保存当前规范名称和仍在使用的简称，不保存历史误称、错误材质、被纠正版本、纠错叙事或失效别名；历史冲煮记录可以保留原始文本，读取时临时解析到当前 `canonical_id`，但不把旧标签写回主档；
4. 完成解析后去重，一个规范实体在候选池中只能出现 1 次；同品牌或同系列的不同版本继续保持独立；
5. 再建立可用性台账，只有用户明确拥有、当前会话明确可用或本杯明确借用的实体可以进入候选池；
6. 对每只滤杯保留全部已核实滤纸接口，每个接口按形状、标称尺寸/型号、成形方式、必要工具/组件和适用底座定义；品牌不作为接口条件。对具体滤纸保留完整产品线/SKU、尺寸/型号、原生形态与材质，并映射到相应接口；同品牌的不同流速系列、Wave/锥形/圆片与不同尺寸分别建实体。外部商品图片出现某型号但用户未确认拥有时，只建立 `research_only` 条目。

冲突解析使用以下优先级：当前消息的最新明确条件/纠正 > 当前会话的已确认状态 > `private-coffee-profile.md` 的当前有效字段 > 购买/冲煮历史线索 > 助理匹配与公开资料。公开制造商页面可以核对某型号的结构事实，但不能反向证明用户拥有该型号；购买邮件可以提示身份和时间线，但不能覆盖用户对当前实体、材质、版本或库存状态的明确纠正。用户明确说“从未拥有”时，从当前库存、有效简称映射与候选池中删除该对象；只有用户明确要求更新私人主档时才持久化这一变化。

候选池与证据池使用不同角色：

| 角色 | 能否进入当前器材候选池 | 允许用途 |
|---|---:|---|
| `owned_current` | 是 | 个人档案确认当前拥有 |
| `session_available` | 是 | 当前对话明确可用 |
| `borrowed_this_brew` | 是 | 只供本杯或本轮使用 |
| `historical_use` | 否 | 解释旧配方、身份或经验 |
| `purchase_record` | 否 | 身份与购买历史线索 |
| `practice_case_equipment` | 否 | 外部方法、观察和迁移案例 |
| `competition_case_equipment` | 否 | 比赛系统案例与迁移证据 |
| `research_only` | 否 | 制造商、测试或一般对象研究 |

同一规范实体可以同时在不同资料中出现，但角色必须分别证明。例如某滤杯出现在比赛案例中，只说明存在外部案例；只有它还在当前请求或私人库存中被确认可用时，才以独立的可用性依据进入候选池。禁止从品牌相同、方法相似、比赛选手使用或历史购买自动推导当前拥有。

### 追问与状态变化

收到追问后先判断其功能：

| 追问类型 | 状态处理 | 输出处理 |
|---|---|---|
| 解释某个参数或机制 | 先核对原依据；依据成立时保持状态 | 补充理由、证据和联动 |
| 补充来源或改变格式 | 写为 `response_only` | 只改变本次回答 |
| 指出方案依据、适配或协同问题 | 建立当前方案的 `correction` 事件 | 沿依赖关系重审并输出完整方案 |
| 修改下一杯参数或器材 | 更新 `coffee_case` 或 `brew_attempt` | 重审所有依赖项并生成完整方案 |
| 提供上一杯新结果 | 写入当前 `coffee_case` 的 observation | 更新机制权重并生成下一轮 |
| 开始另一支咖啡 | 创建新 `coffee_case` | 使用新对象完整输出 |
| 声明长期默认或全会话规则 | 更新相应广域 scope | 后续相关案例按优先级继承 |

如果用户问“为什么是 40 秒”，先解释原方案，不把 40 秒登记为默认值。如果用户说“我的默认是 30 秒”，把 30 秒登记为 `profile_global` 默认；当前方案需要使用其他时长时，另建 `brew_attempt` 临时覆盖。

用户指出配方问题时，这条消息首先修正当前方案或其依据。只有消息同时明确表达长期器材事实、个人默认或稳定偏好时，相关部分才进入广域档案。实质纠错需要记录被挑战前提、失效决定、重新确认参数和改变参数；未被用户点名的项目也根据依赖关系重新核对。

长对话可能经历上下文压缩。当前决定依赖精确型号、库存、单位或默认值时，优先读取持久档案；只有会话资料时，先用已有明确事实，必要时用一个集中问题核对会改变方案方向的字段。

## 四、持久私人档案

用户明确要求建立、记住、保存或更新长期资料时，只创建或更新唯一私人文件 `private-coffee-profile.md`。实际数据归用户个人空间管理，通用 skill 文件包只保留本规范；不得再创建器材对象登记、环境摘要或其他平行私人文件。

推荐结构如下：

```markdown
# 私人手冲咖啡主档

## 元数据
- 最后更新时间：
- 当前版本：

## 器材身份与客观对象缓存
| Canonical ID | 当前有效简称 | 规范品牌与完整产品名 | 尺寸 | 材质 | 版本/联名/组件 | 主体几何与出口/阀门 | 全部兼容接口：形状、型号、成形方式、工具/组件 | 来源 URL | 核实日期 | 可用性角色 | 当前状态 |

## 滤纸与用水
| Canonical ID | 当前有效简称 | 品牌与完整产品线/SKU | 尺寸/型号/原生形态/材质 | 接口代码与成形方式 | 来源 URL | 核实日期 | 当前状态 | 用户确认日期 |

## 个人默认值
| 字段 | 数值/规则 | 计时或单位定义 | 适用范围 | 确认日期 |

## 稳定偏好
| 表述 | 专业评价中的对应维度 | 证据状态 | 确认日期 |

## 优化策略
| 字段 | 当前规则 | 适用范围 | 当前请求覆盖方式 | 确认日期 |

## 对象级历史索引
| 咖啡身份 | 购买记录位置 | 冲煮记录位置 | 当前库存状态 |

## 候选模式与历史状态
| 内容 | 支持案例 | 当前等级 | 待确认事项 |
```

### 器材身份层

器材档案负责让运行时能够准确定位用户拥有的实物。每个对象至少保存：

1. 唯一 `canonical_id`、用户常用简称和仍然有效的别名；
2. 规范品牌和产品名称；
3. 尺寸、材质、代际、联名、颜色或特殊表面处理等必要区分字段；
4. 中文、英文、原始语言、当前有效简称和型号组成的检索种子；
5. 当前拥有、暂时可用、本杯借用、用完、停用或历史使用等可用性角色及其来源；
6. 用户确认日期，以及必要的照片、包装或购买页面线索；
7. 可以稳定复用的客观字段：主体几何、材质、尺寸、出口/阀门/活动组件，以及按形状、标称尺寸/型号、成形方式、必要工具/组件和适用底座定义的全部已核实滤纸接口、原始来源 URL 与核实日期。

客观缓存用于避免每次配方重复确认 20 多个滤杯和滤纸的基本身份。滤杯缓存命中需要完整型号、尺寸、材质、版本/联名与当前组件相符；滤纸缓存命中需要完整产品线/SKU、形状、标称尺寸/型号与材质相符。兼容性先按接口的形状、尺寸/型号、成形方式与工具匹配，再由具体滤纸产品的材质和批次进入水力分析；品牌只识别产品，不决定兼容。滤杯—滤纸实际贴合、非原生折法、旁路、有效粉床几何、湿态阻力、批次差异、当前组合水力学、热表现、配方迁移、厂商性能/感官声称、第三方测试、比赛案例和个人观察仍属于运行时研究或案例证据，不能作为客观缓存。

主档不得保存制造商或第三方的“更快、更甜、更干净”等性能主张、配方、流速排名、感官观察、个人杯测结果、单杯表现、机制推断或纠错历史。若客观字段发生变化，直接更新当前值和核实日期；不要保留已经失效的误称、错误材质或旧映射。

### 探索与有限豆量策略

私人档案可以记录 `exploration_preference`、`risk_tolerance`、`limited_coffee_policy` 和 `experience_coverage`，用于解释用户如何权衡完整系统中的专业质量、目标匹配、表达覆盖、信息与体验增量、执行风险和咖啡消耗。这些字段只调整“优化下一杯”时各维度的权重，不另设复制、探索或实验目标。

不得从“拥有很多滤杯”“曾经换过器材”或某次正面/负面记录自动推导稳定探索策略。只有用户明确说明一般倾向，才写为 `profile_global`；“这支豆想多试几个滤杯”“最后一杯要给朋友喝”分别属于 `coffee_case` 或 `brew_attempt`，不能污染其他咖啡。

通用 Skill 不预设有限豆量必然要求保守，也不预设必然要求探索。私人档案可以明确有限杯数更重视差异化体验与对象覆盖、单杯成功率，或二者平衡；当前请求对本杯的明确目标始终可以临时覆盖该档案规则。

### 更新规则

用户明确给出的库存变化、默认值和身份纠正可以直接更新。修改时更新主档时间；器材换代、耗材用完或水源停用时直接写当前状态。历史冲煮数据可以在其原记录中保留原始标签，但私人主档只呈现当前有效事实。

结构化购买记录用于确认对象身份和历史暴露，当前库存需要用户明确说明或有库存字段支持。结构化冲煮记录用于对象级历史和候选模式，聚合中位数继续作为条件化先验。

## 五、首次建档流程

用户希望预先建档时，分批接收资料，避免一次要求完整历史：

1. 当前磨豆机、刀盘、滤杯、冲煮器和手冲壶；
2. 当前滤纸、基础水、矿物液和常用调水方式；
3. 计时起点、默认粉量、闷蒸和研磨记录方式；
4. 稳定感官目标、探索与风险倾向、有限豆量策略及其与专业质量判断的关系；
5. 可选的购买记录和近期冲煮记录。

对只有简称的器材，先利用照片、包装、购买页面和公开资料解析规范身份。一次集中询问能够消除最大身份歧义的问题，并在已有信息足够时继续建立其他条目。

## 六、每次运行的资料流程

1. 读取当前消息、附件和本轮明确目标。
2. 判断当前消息属于现有咖啡延续、解释/格式追问、下一杯修改，还是新咖啡案例。
3. 为新信息写入 `kind`、`scope`、`applies_to`、`expires_after`、`source_turn` 和 `status`。
4. 合并同一对话中与当前对象和任务相关的有效资料。
5. 当前决定依赖既有库存、器材简称、滤纸、默认值或历史时，只读取 `private-coffee-profile.md`；复用精确匹配的客观缓存字段。
6. 依据优先级解决冲突，把当前有效简称解析到规范实体；历史标签只在读取原记录时临时解析，不写回主档；产品图片和研究资料不建立个人可用性。
7. 为每个器材声明可用性角色与来源，只用当前可用实体建立候选池；外部案例器材保留在证据池。
8. 标记个人默认、探索与有限豆量策略、会话规则、对象条件和单次覆盖。
9. 用规范身份开展当前咖啡、烘焙商、生豆和产季的实时研究；器材与用水先复用精确匹配的客观缓存，再增量研究缺失、冲突、版本敏感和组合级字段，为实际候选建立主体、当前组件和精确滤纸组成的系统身份卡。
10. 把每条历史冲煮绑定原始 `case_id + brew_id`，分开配置、观察、用户解释与 Skill 推断；迁移时建立共享条件和差异。
11. 出现实质纠错时，从最后一个仍有效的上游决定重新运行路线选择、系统共同求解和参数协同检查。
12. 以独立的“当前对象研究与分析”章节呈现研究结论，再完成专业判断、路线选择和完整方案。
13. 将新结果保留在对应 `coffee_case`；完成 `response_only` 和到期的 `brew_attempt` 后结束其作用。
14. 用户要求持久保存时，只更新被明确指定且已经确认的字段。
