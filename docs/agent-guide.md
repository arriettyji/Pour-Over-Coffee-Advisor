# Agent 与维护者导览

本文件面向需要理解、审阅或维护 Pour-over Coffee Advisor 的 Agent 与项目维护者。普通使用者从根目录 [`README.md`](../README.md) 开始；运行具体咖啡任务的 Agent 以 [`SKILL.md`](../SKILL.md) 为权威入口，并只按当前问题加载相关 reference。

## 1. 文件职责

| 文件或目录 | 职责 |
|---|---|
| `SKILL.md` | 触发范围、输入状态、对象研究、分析流程、配方生成、上下文作用域、证据追踪、输出合约和交付检查 |
| `references/evidence-policy.md` | 证据分类、来源等级、实践观察与解释的分离、迁移规则 |
| `references/runtime-research/object-research.md` | 当前产品、烘焙商、生产背景、产区/产季、可迁移经验和器材/水的并列研究方法 |
| `references/reasoning/analysis-engine.md` | 初次冲煮、诊断、路线选择、器材筛选、粉量传播、时间预测和连续验证的分析框架 |
| `references/theory/` | 生产与生豆、烘焙、冲煮和感官的稳定理论入口及底层研究记录 |
| `references/practice/` | 文章、视频、比赛方案、器材案例、实践综合卡和来源索引 |
| `references/personal-profile.md` | 无档案、会话资料和持久私人档案的接入规范，不包含任何具体用户的私人档案 |
| `references/research-status.md` | 研究数量、资料性质、首版能力范围与主要证据缺口 |
| `evals/` | 行为案例、失败签名和评分标准 |
| `agents/openai.yaml` | Skill 列表和调用界面使用的显示名称、简短说明与默认请求 |

## 2. 推荐加载顺序

处理具体任务时按以下顺序加载资料：

1. 完整读取 `SKILL.md`，确认任务类型、输入状态和输出模式。
2. 复杂案例读取 `evidence-policy.md`、`object-research.md` 和 `analysis-engine.md`。
3. 只加载当前决定需要的理论主题文件；需要核查底层出处、方法或限制时，再进入相应 `studies-*`、`research-audit.md` 和 `source-register.md`。
4. 先用 `references/practice/README.md` 路由实践资料，再进入综合卡、器材案例、比赛案例或文章研究记录。
5. 如果任务依赖用户过去的器材、耗材、默认值或偏好，读取个人上下文规范，并只在用户已经启用时接入唯一私人文件 `private-coffee-profile.md`。

不要把整个知识库一次性加载进上下文。主题文件和综合卡是运行时入口，底层记录用于核查和补充，并不因未被本次加载而失去效力。

## 3. 每个案例的运行流程

### 3.1 建立输入状态

将请求整理为 6 组并标注 `已确认 / 暂定 / 缺失`：

1. 咖啡与当前样品状态；
2. 烘焙商与烘焙背景；
3. 器材与用水；
4. 可控冲煮参数；
5. 冲煮过程与感官结果；
6. 用户当前目标。

为当前咖啡建立独立 `case_id`，再判断新消息属于新的冲煮结果、下一杯条件、解释追问、新咖啡，还是个人档案更新。

### 3.2 完成对象研究

具体对象任务并列研究 6 个维度：

1. 当前产品和样品状态；
2. 烘焙商长期风格及近期变化；
3. 生产者、庄园/地块、品种和处理背景；
4. 产区与当前产季；
5. 共享明确条件的可迁移经验；
6. 滤杯、滤纸、磨豆机/刀盘和用水的精确身份与结构。

产品页面完整也不跳过其他维度。找不到公开资料时记录缺口，不使用行业常识伪装成当前对象事实。完整配方回答始终设置独立的“当前对象研究与分析”章节。

### 3.3 解析器材系统

先将用户简称映射到唯一规范实体，确认型号、尺寸、材质、版本、组件和当前可用性，再建立每只滤杯的兼容接口清单。滤纸兼容按形状、尺寸/型号、成形方式、必要工具和适用底座判断；滤纸品牌只用于识别精确产品。

为本轮候选建立滤杯—滤纸系统身份卡，包含滤杯本体、出口拓扑、当前底座或阀门、精确滤纸产品线、实际贴合/折法、旁路和有效粉床几何。实践文章和比赛案例中的器材属于证据池，只有具有明确当前可用性依据的器材进入用户候选池。

### 3.4 选择路线并构造方案

已有结果时比较 4 条路线：精修当前系统、保留器具但重构、换滤杯或滤纸并重构、使用 2 条实质不同的完整方向并行探索。上一杯无论正面或负面都只是证据，不自动拥有下一杯的路线优先权。

滤杯、滤纸和粉量共同求解。用户指定粉量时，将其作为确定输入传播到总水量与饮料量、床深与阻力、研磨、润湿、每段注水、流量、水位、扰动、热管理、预计总时和结束条件。

预计总时使用逐段状态传播：段初状态 → 注水输入 → 注水期间同步排液 → 段末水位/液体库 → 段间排液 → 下一段起始状态。最后注水结束加末段排液只能作为事后记账关系，不能代替预测过程。

## 4. 上下文与私人资料

会话信息使用 5 级作用域：

| 作用域 | 使用范围 |
|---|---|
| `profile_global` | 长期器材、稳定默认和明确偏好，可以进入不同咖啡并由当前请求覆盖 |
| `session_global` | 用户明确指定当前对话共同采用的临时规则 |
| `coffee_case` | 当前咖啡的样品状态、结果、目标和限制 |
| `brew_attempt` | 下一杯指定器材、水、动作或实验条件，完成或改变后到期 |
| `response_only` | 来源、解释、格式或比较角度，只影响本次回答 |

新咖啡只继承个人全局和仍然有效的会话全局状态。单次记录能够直接说明某个 `case_id + brew_id` 下的完整配置和结果，但任何单参数因果解释仍需验证；跨咖啡或跨器材迁移时必须写明共享条件和改变边界。

通用项目不包含具体用户档案。持久状态只使用用户明确启用的唯一 `private-coffee-profile.md`，当前消息和当前会话具有更高优先级。主档保存当前有效的规范身份和明确事实，不保存历史误称、纠错叙事或 Agent 推测。

## 5. 稳定输出合约

完整模式的核心决定包括：

1. 当前对象研究与分析；
2. 技术判断与路线结论；
3. 方案摘要表和注水时间轴表；
4. 参数协同、关键依据与预期结果；
5. 观察重点和后续判断。

多个器材竞争、粉量处于适配边缘或正在迁移时，增加滤杯与滤纸选择图谱；存在竞争机制时增加关键假设与替代解释；来源冲突时展开证据性质与分歧；存在高价值的另一杯型时提供第 2 条同等完整方案。

解释型或来源型追问使用增量模式，并保持原配方状态。追问改变可执行参数，或发现身份错误、无依据假设、条件冲突和遗漏的关键相互作用时，重新审计依赖关系并生成独立可执行的完整方案。

所有定量信息使用阿拉伯数字。执行方案集中使用表格，分析部分使用完整段落；参数理由可以合并表达，但滤杯—滤纸选择、粉量传播、时间状态和关键证据不能因篇幅压缩而随机缺失。

## 6. 证据与迁移

关键决定区分 `[稳定知识]`、`[实践观察]`、`[实践解释]`、`[对象事实]` 和 `[当前推断]`。制造商可以提供型号、结构和兼容性事实，但性能与感官主张仍按实践解释处理。

跨对象经验分为直接信息、较强先验、较弱先验和待验证推断。每项重要迁移记录原对象、共享条件、支持的窄判断、关键差异、迁移等级和下一步验证。来源数量、品牌声望和比赛名次不构成机制证据，也不提高器材的当前适配度。

## 7. 维护原则

- `SKILL.md` 是运行规则的单一权威来源；README 与本导览解释项目，但不建立平行行为规则。
- 固定理论、实践资料和对象研究分别保存，更新时维持原有证据类型和来源位置。
- 新增底层研究记录时同步更新研究审计与来源登记；新增综合卡时不要用综合卡数量替代底层研究量。
- 私人档案、购买记录、完整冲煮数据库、建设阶段原始附件和本地测试材料不进入公共项目。
- 行为修改使用 `evals/` 中对应案例检查；新增失败模式时补充可观察的验收标准和失败签名。
- README 中的公开能力描述、研究数量和文件链接应随项目版本保持一致。

更细的执行约束和交付检查均保留在 `SKILL.md`。本导览只负责解释文件关系与加载路线，不能替代运行入口。
